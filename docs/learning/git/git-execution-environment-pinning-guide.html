你在解析另一個程式的輸出時，使用者的設定就是你的輸入

一個號稱唯讀的工具，只要用子行程讀 git diff 的輸出，它的真正輸入就不只是 repository：使用者的 ~/.gitconfig、繼承來的環境變數、以及 repo 裡的 .gitattributes 都會改變那份輸出的形狀，甚至讓工具在別人的機器上留下背景行程。本文把「釘住執行環境」整理成可套用的判斷方法：三個影響管道各自要用不同手段封住，而且不是每個設定都該封。

實務情境：一條看起來很單純的唯讀管線

假設你在寫一個本機的程式碼審查 CLI。使用者在 repository 裡執行一個命令，工具做四件事：列出有變更的檔案、逐檔讀出 patch、把 patch 解析成 hunk、依 token 預算挑選 hunk 後送給模型。四個步驟都是唯讀的，沒有任何 git add 或 git commit。

這種管線有四個前置條件，缺一個，後面的討論就不成立：

  • 你在解析輸出，而不只是看 exit code。你依賴 stdout 的結構：哪一行是 diff --git、context 行的第一個字元是空白、@@ 的數字要對得上實際行數。
  • 那個結構由使用者可寫的設定決定。git 有數十個影響 diff 輸出外觀的設定鍵，全部都在使用者的控制之下。
  • 你對外聲稱唯讀。使用者相信跑這個命令不會動到他們的 repository。
  • 錯誤代價高。解析失敗會中斷整個審查；更糟的是解析「成功」但語意錯了，錯誤內容會被送到下游（模型、報表、行號標註）。

本文所有實測都在 git 2.39.0 的臨時 repository 上完成，並以這條管線當作唯一的貫穿例子。

直覺做法為什麼不夠

直覺的寫法是「把該加的旗標加上就好」：--no-color 避免 ANSI escape、--no-ext-diff 擋掉外部 diff 程式、--unified=3 固定 context 行數，然後假設 exit code 為 0 且 stdout 非空 = 輸出可解析。

這個假設在使用者的真實機器上會以兩種方式破掉，而它們的偵測難度差很多。

吵的破法：輸出形狀變了，parser 直接失敗

如果使用者設了 diff.suppressBlankEmpty=true，空白的 context 行不再是「一個空白字元」，而是真正的空字串：

Shell$ git -c diff.suppressBlankEmpty=true diff HEAD -- f.txt \
    | sed -n '5,9p' | sed 's/^/[/;s/$/]/'
[@@ -1,3 +1,4 @@]
[ a]
[]                 # ← 原本應該是 "[ ]"
[ b]
[+c]

嚴格的 parser 會拒絕這一行，因為它的第一個字元不是 ' '、'+'、'-' 之一。同一類的還有 diff.submodule=log：submodule 指標變更會變成一段 commit log，整個 record 連 diff --git 這一行都沒有，parser 找不到 record 邊界。

這類問題雖然造成整體失敗，但至少會叫。你會拿到一個明確的 parse 錯誤，加一條 pin 就修好。

靜默的破法：輸出仍然合法，但語意已經錯了

textconv 是最好的例子。它的設定分成兩半：使用者的 gitconfig 定義轉換命令，repo 的 .gitattributes 指定哪些路徑要套用。

Shell$ git config diff.mydriver.textconv ./conv.sh   # 使用者設定
$ cat .gitattributes                            # repo 內容
doc.bin diff=mydriver

$ git diff HEAD --no-color --no-ext-diff --unified=3 -- doc.bin
                   # ← 空輸出，但檔案真的改了

$ git diff HEAD --no-color --no-ext-diff --no-textconv \
    --unified=3 -- doc.bin
diff --git a/doc.bin b/doc.bin
@@ -1,2 +1,3 @@
 secret-real-line-1
 secret-real-line-2
+secret-real-line-3

轉換器把新舊兩個版本都變成同一段文字，於是 git 認為「沒有差異」而輸出空字串。注意這裡有兩件事同時發生：--no-ext-diff 沒有擋住它（那是另一套機制），而列舉步驟用的 --name-status 不讀內容，所以它照樣回報這個檔案是 M。

結果是管線內部自相矛盾：列舉說有變更、patch 卻是空的。在我們的實作裡，tracked 檔案的空 patch 被視為「檔案在列舉與讀取之間消失了」，整個審查以 exit 1 收場：

Shell$ reviewstuff review --json
Changed file became unavailable while reading the diff: doc.txt [working-tree].
exit=1

而如果轉換結果有差異，情況更隱蔽：管線會成功跑完，但送給模型的是轉換器的輸出，於是回報的行號指向轉換後的文字，不是使用者檔案裡的行。沒有任何錯誤訊息告訴你這件事。順帶一提，git 會對每個 blob 版本各跑一次轉換器（一個檔案兩次呼叫），大 diff 下就是額外的 2N 個子行程，直接吃掉你為 diff 設定的時間預算。

容易誤判的相鄰旗標：--no-ext-diff 停用的是 external diff driver，--no-textconv 停用的是 textconv filter。兩者是不同機制，加了前者不會關掉後者。

第三種破法：唯讀命令產生持久副作用

不是所有問題都出在輸出。列舉未追蹤檔案的 git ls-files --others 在 core.fsmonitor=true（很多人為了加速 git status 會開）之下會啟動 git 的檔案系統監控 daemon：

Shell$ pgrep -f "fsmonitor--daemon" | wc -l
0

$ GIT_OPTIONAL_LOCKS=0 git -c core.fsmonitor=true \
    ls-files --others --exclude-standard -z
untracked.txt

$ pgrep -fl "fsmonitor--daemon"
17162 git fsmonitor--daemon run --detach --ipc-threads=8
      # ← 命令結束後仍存活

一個 --detach 的背景行程留在使用者的 repository 上，而且 GIT_OPTIONAL_LOCKS=0 完全管不到它（那個環境變數只管 index lock）。core.fsmonitor 還有另一種用法：指向一個 hook 腳本（Watchman 整合）。這時 git 會執行那支程式，我們的實測顯示兩個命令共觸發了四次呼叫。也就是說，審查期間會跑使用者配置的外部程式；如果那支程式卡住，你的掃描就跟著卡住。

心智模型：三個影響管道，三種手段

把上面的例子歸納一下，會發現使用者的設定是透過三個不同的管道流進 git 的，而每個管道只有特定手段能封住。這是整個 pattern 的核心，也是最容易做錯的地方。

管道一：設定檔 → 用 -c key=value

system、global、repo-local 三層 gitconfig 都可以改輸出形狀。命令列的 -c 優先於全部設定檔，也優先於 GIT_CONFIG_PARAMETERS：

Shell$ export GIT_CONFIG_PARAMETERS="'diff.noprefix=true'"

$ git diff -- f.txt | head -1
diff --git f.txt f.txt          # 設定生效，前綴消失

$ git -c diff.noprefix=false diff -- f.txt | head -1
diff --git a/f.txt b/f.txt      # -c 贏

這一點很重要，因為 a/、b/ 前綴是我們判斷「這個 record 講的是哪個路徑」的依據；前綴被拿掉，路徑歸屬就會失敗。

管道二：環境變數 → 只能 unset 或設成固定值

有些行為完全不存在對應的設定鍵，因此 -c 無能為力。GIT_DIFF_OPTS 就是這樣，而且它會蓋掉你在命令列明確指定的旗標：

Shell$ git diff --unified=3 -- ctx.txt | grep '@@'
@@ -3,4 +3,4 @@ b

$ GIT_DIFF_OPTS=--unified=0 \
    git diff --unified=3 -- ctx.txt | grep '@@'
@@ -6 +6 @@ e                    # context 行全部消失

同一個管道還有 GIT_DIR、GIT_WORK_TREE、GIT_INDEX_FILE 這類會把命令導向另一個 repository 的變數——當你的 CLI 提供「指定 repository 路徑」的選項時，繼承來的這些變數會讓工具實際讀到別的地方。處理方式是在建立子行程時把它們明確移除，而不是信任呼叫者的環境。

管道三：per-path attribute → 只能用 CLI 旗標

textconv 屬於這個管道：.gitattributes（repo 內容）決定哪些路徑套用哪個 driver，driver 的實際命令則在使用者設定裡。你無法用 -c 關掉它，因為要關的鍵是 diff.<driver>.textconv，而 <driver> 的名字是 repo 自己取的，你事前無法列舉。唯一能全面停用的方式是 CLI 旗標 --no-textconv。

判斷順序：先問「這個行為是被 config key、環境變數，還是 per-path attribute 觸發的」，再決定手段。把三者混為一談，就會出現「我明明加了 -c，怎麼還是被影響」這種找不到原因的狀況。

每一條 pin 對應一個症狀

Pin 清單很容易長成一堆看不出用途的字串。維護它的辦法是讓每一條都能回答「移除它會看到什麼症狀」，並記錄哪些看似相關的手段擋不住它。

手段 管道 移除後觀察到的症狀 擋不住它的手段
-c diff.suppressBlankEmpty=false 設定檔 空白 context 行變空字串，parser 拒絕整份 patch 任何 CLI 旗標
-c diff.submodule=short 設定檔 submodule 變更沒有 diff --git 行，找不到 record 邊界 --no-ext-diff
-c diff.noprefix=false、-c diff.srcPrefix=a/、-c diff.dstPrefix=b/、-c diff.mnemonicPrefix=false 設定檔 a/、b/ 前綴被改寫或移除，record 無法歸屬到路徑 任何 CLI 旗標
-c core.fsmonitor=false 設定檔 唯讀命令留下 --detach daemon，或執行使用者的 hook 程式 GIT_OPTIONAL_LOCKS=0
--no-textconv per-path attribute patch 變空或內容被替換，行號指向轉換後的文字 -c、--no-ext-diff
unset GIT_DIFF_OPTS 環境變數 明確指定的 --unified=3 被覆蓋，context 行消失 -c（不是 config key）
unset GIT_DIR、GIT_WORK_TREE、GIT_INDEX_FILE 環境變數 命令作用在繼承環境指定的 repository，而不是使用者選定的那個 -c、CLI 旗標
GIT_OPTIONAL_LOCKS=0 環境變數 掃描 untracked 檔案時把快取寫回 index，唯讀操作變成寫入 -c（可用 core.untrackedCache=false，但已被此變數覆蓋）

表格最後一列示範了另一個實用結論：pin 之間會互相覆蓋，重複的要拿掉。我們實測 core.untrackedCache=true 搭配 GIT_OPTIONAL_LOCKS=0 跑 ls-files --others，index 檔案的 mtime 與大小完全沒變（2226 bytes → 2226 bytes）；把環境變數拿掉後改跑 git status，index 立刻長到 2589 bytes。既然環境變數已經封住這條路，就不必再加 core.untrackedCache=false——多餘的 pin 會讓清單失去「每條都在防一個具體症狀」的可讀性。

在程式裡怎麼放

把三種手段集中在建立子行程的那一層，而不是散在各個呼叫點。設定與環境屬於「每個命令都一樣」的部分，可以做成常數前綴；per-path 旗標只加在真正讀內容的命令上：

TypeScript// 每個 git 命令都帶的設定 pin
const gitConfigArguments = [
  "-c", "core.quotePath=false",
  "-c", "core.fsmonitor=false",
  "-c", "diff.noprefix=false",
  "-c", "diff.mnemonicPrefix=false",
  "-c", "diff.srcPrefix=a/",
  "-c", "diff.dstPrefix=b/",
  "-c", "diff.relative=false",
  "-c", "diff.suppressBlankEmpty=false",
  "-c", "diff.submodule=short",
] as const;

// 環境：固定值用字串，要移除的用 undefined
const gitCommandEnvironment = {
  LC_ALL: "C",
  GIT_OPTIONAL_LOCKS: "0",
  GIT_DIFF_OPTS: undefined,
  GIT_DIR: undefined,
  GIT_WORK_TREE: undefined,
  GIT_INDEX_FILE: undefined,
} as const;

per-path 旗標放在哪裡：設定與環境屬於每個命令都一樣的部分，因此做成常數前綴；--no-textconv 只加在真正讀內容的命令上（讀 tracked patch 的 diff 與讀 untracked 檔案的 diff --no-index），列舉用的 --name-status 不讀內容所以不需要。

用 undefined 表示「移除」需要下層真的支援：Node 的 child_process 在組合環境時會跳過值為 undefined 的鍵，所以 { ...process.env, GIT_DIR: undefined } 的效果是子行程完全看不到 GIT_DIR，而不是看到空字串。如果你的 spawn 封裝會把 undefined 轉成 ""，這個寫法就是錯的——空字串對某些 git 變數而言是有意義的值。

怎麼確認自己 pin 對了：每條 pin 都要有一個會失敗的 fixture

Pin 清單最大的風險是「以為有效」。驗證方法很機械：為每條 pin 建一個臨時 repository fixture，重現該設定，斷言流程能跑完；然後把那條 pin 移掉重跑，測試必須變紅。我們在加入 diff.submodule 與 --no-textconv 時就是這樣確認的——如果拿掉 pin 測試仍然綠燈，那條 pin 防的不是你以為的東西。

副作用類的 pin 不能只看輸出，要找可觀察的指標：

  • 是否寫入：比對命令前後 .git/index 的 mtime 與大小。
  • 是否留下行程：命令結束後 pgrep 目標 daemon。
  • 是否執行外部程式：讓 hook 腳本 append 到 log 檔，再檢查 log。

不要 pin 什麼：忠實度的邊界

「全部釘住」是很自然的直覺，但它會把工具變成一個不尊重使用者偏好的黑盒。判準是：只 pin 會破壞解析或造成副作用的鍵，不 pin 只影響內容偏好的鍵。

以 diff 為例，diff.algorithm（myers／histogram）、diff.indentHeuristic、diff.interHunkContext 都會改變 hunk 的切分與分組方式，但它們產生的輸出結構完全合法：record 邊界、a/ 前綴、context 行的第一個字元都不變。它們影響的是「哪些行被歸成一組」，那是使用者對可讀性的偏好，pin 掉只會讓工具看到的 diff 與使用者自己看到的不一致。同理，如果使用者要求忽略空白差異，那應該是一個你主動支援的選項，不是要封住的干擾。

比較兩個更簡單的替代方案

方案一：整批忽略使用者設定

最省事的想法是 GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null，一次擋掉所有使用者設定，不用維護 pin 清單。問題是它蓋不住 repo-local 的 .git/config：

Shell$ git config diff.noprefix true      # 寫進 repo-local
$ export GIT_CONFIG_GLOBAL=/dev/null
$ export GIT_CONFIG_SYSTEM=/dev/null

$ git diff -- f.txt | head -1
diff --git f.txt f.txt               # ← 仍然生效

$ git -c diff.noprefix=false diff -- f.txt | head -1
diff --git a/f.txt b/f.txt           # 只有 -c 真的封住

而且它是把嬰兒跟洗澡水一起倒掉：safe.directory、credential helper、includeIf 等使用者需要的設定也一起消失。它可以當作額外的一層，但不能取代 -c。

方案二：不 pin，改成寬鬆解析

另一條路是接受輸出不可控，改讓讀取端容錯：輸出超限就截斷並標記、空輸出就跳過該檔案、解析不出來就當成沒有變更。這在「輸出只是給人看的預覽」時是完全合理的選擇——顯示端可以少一塊內容，但不會壞掉。

它不適合我們的前置條件，因為那些錯誤剛好會靜默地變成錯誤答案：textconv 造成的空 patch 會被解讀成「這個檔案沒有變更」，於是它從審查範圍裡消失，而使用者以為它被審查過了。當下游要做覆蓋率統計與行號標註時，「安靜地少一塊」比「大聲失敗」危險得多。

釘住執行環境 寬鬆解析
優化的性質 輸出形狀可預測，錯誤大聲 永不因設定而中斷
接受的代價 要維護一張 pin 清單與對應 fixture 語意錯誤不會被發現
適用條件 輸出餵給程式：覆蓋率、行號、預算計算 輸出給人看：預覽、摘要

什麼情況不需要這個 pattern

  • 你只看 exit code 或單一 token。git rev-parse --is-inside-work-tree 這類輸出不受 diff 設定影響，不需要整套 pin。
  • 你在自己完全控制的環境裡跑（CI 容器、固定映像檔），而且明確驗證過那裡沒有使用者設定；此時 pin 是多餘的複雜度。不過要注意：repo 內的 .gitattributes 仍然來自被檢查的內容。
  • 你的輸出直接給人看且允許誤差。如上一節所述，寬鬆解析更省事。
  • 你要刻意反映使用者偏好。如果產品定位是「顯示使用者自己會看到的 diff」，那 pin 掉他的 diff 設定就是錯的行為。

帶得走的五個診斷問題

  1. 我實際在解析哪幾個位元組？把依賴的結構列出來（record 邊界、路徑前綴、行首字元、數字欄位），再去該工具的文件裡找哪些設定會動到它們。
  2. 這個行為是從哪個管道來的？config key 用 -c、環境變數用 unset、per-path attribute 用 CLI 旗標。選錯手段等於沒封。
  3. 出錯時會叫還是安靜？安靜的那些（內容被替換、輸出變空、行號位移）必須有 fixture，因為沒有人會通報它們。
  4. 這個「唯讀」命令會不會寫入或起行程？用 index mtime、pgrep、hook log 這類可觀察指標實測，不要憑文件推斷。
  5. 這條 pin 拿掉之後，哪個測試會紅？答不出來就代表它是裝飾，或者它防的東西你其實沒驗證過。
